This fifteenth release candidate opens Markdown, HTML and PDF attachments, and an Agent's answers, in the reader beside the chat; it puts a room's information on one page, with tiles that add and remove members, the room's name and a nickname of your own; and it opens Moments inside the chat window. It also corrects member lists that kept a person who had been removed, and no longer leaves a card under a message for a run that completed. Everything that was new in rc.10, rc.11, rc.12, rc.13 and rc.14 is included and is listed below.

**Read before upgrading**

- **Desktop executable name.** The command and process name is now `hagency` (`hagency.exe` on Windows). Update scripts or shortcuts that point directly to `rinx`. On macOS, if Hosting Options offers **Use this app’s service**, select it to update a hosting service registered to the previous executable. On Windows, close the previous Desktop and select **Uninstall before installing** when the installer offers it. Keep the app data option unchecked to retain your account and local data.
- **Do not go back to rc.9 or earlier on a computer that hosts Agents.** Since rc.10 the Desktop keeps an Agent's reports as a new kind of record in that Agent's encrypted message store, and an earlier build cannot read a store that holds one.
- **Going back from rc.14 to rc.13 on a computer where rc.14 set up hosting.** rc.13 knows one hosting set-up per computer, in the place where rc.13 and earlier builds made it, and rc.14 leaves a set-up it finds there where it is. A set-up that rc.14 makes for an account that had none on that computer, a further account or the first one of a new installation, is kept in a folder of its own, which rc.13 does not read: under rc.13 that account does not host. The folder stays and is used again under rc.14. Do not set up hosting for the same account under rc.13 meanwhile: rc.14 would then find two set-ups for one account and refuse that account's hosting.
- **Going back from rc.13 to rc.12 on a Mac that hosts a Claude pool in containers.** rc.12 does not read the container choice: that pool's Agents run in the macOS sandbox again, and each member's next message starts a new conversation with the Agent. The choice is kept in the hosting folder and applies again under rc.13.
- **Going back from rc.12 to rc.11 on Windows.** Where rc.12 has repaired the permissions of an account folder and set a history list it could not read aside (see below), keep that profile on rc.12 or later. rc.11 does not know the set-aside list, and its clean-up of unused chat databases may remove a database that list named.
- **Going back to rc.10.** rc.10 ignores a role saved by rc.11 or later, so the Agent is without it again. One case does not go back: where rc.11 or later has set a saved sign-in aside because its key was missing (see below), keep that profile on rc.11 or later. An earlier build does not know the set-aside file, and its clean-up of unused chat databases may remove the one rc.11 preserved.
- **Coming from rc.7 or earlier, the hosting database is upgraded at first start, one way.** rc.8 added the tables for Octos resources to the owner's hosting database, and rc.7 and earlier refuse a database upgraded this way: do not go back to such a build on a computer that hosts resources. rc.9, rc.10, rc.11, rc.12, rc.13, rc.14 and rc.15 make no further change to the database's tables.
- **Hosting set-up from rc.5 or earlier is not carried over.** At its first start this build discards the earlier build's resource database, the grant and enrollment journals bound to it and its initializer record, without asking, and begins as a new installation: set up hosting, resources and pools again. Matrix sessions and keys, provider sign-ins, room history and work files are kept. A local-Agent usage record that an earlier build locked as an archive is replaced by an empty one. On a server that supports ledger declarations, the pools and grants published from the discarded database are ended.
- **Saved sign-ins from rc.5 or earlier move into the operating system's credential store at first start, one way.** An earlier build can then no longer open that profile. The macOS build is ad-hoc signed, so macOS treats each new build as a different program and asks for the login password for every saved item after an update.
- The execution machine needs Claude Code 2.1.322 or later and Codex 0.167.0 or later. An older CLI is refused with a message that names the required version. Codex 0.169 works with this build; with rc.9 the room tools of a local Codex Agent failed on it.
- **Server.** A pooled Agent's tool requests now go to the person who sent the message, which needs hagency-server #55; a server without it cannot deliver them. Pooled Claude Agents also need the server to accept a never-started proof for grant version 6 (hagency-server #53). Octos pools need hagency-server #54 as well and, on the execution computer, an Octos build with host-scoped OUP support (octos-org/octos#3260); an older Octos is refused rather than run with weaker isolation. A space's shared project folder needs hagency-server #58. With an older server, the space is created without the folder and each Agent keeps its own. Those four server changes are in the server repository's main line. Two more are needed by rc.10: messages an Agent sends outside a run it was asked for (a timer's turn, a turn it started by itself) need the message authorization of hagency-server #66, and a server without it never delivers them; a pooled Octos Agent's shell requests need hagency-server #59. rc.10's local Agent features were run against a server with #66, at schema 36. rc.15 needs nothing further from the server.

**New in rc.15**

- **Markdown, HTML and PDF attachments open beside the chat.** Opening such an attachment in a chat adds it as a tab in the reader docked beside the chat. The reader keeps its tabs when it is moved into a window of its own and when it is docked again. Markdown is shown by the article reader. An HTML file is shown as a static page that keeps the look it gives itself (its style sheet, classes and table spans), with its scripts, links, forms and everything it would fetch from outside removed. A PDF is drawn by a PDF.js renderer that comes with the installer. The file is downloaded the way the chat downloads it. An HTML or PDF preview is kept in memory and served to the reader from this computer only, under an address bound to the account, for as long as its tab is open.
- **Selecting, finding and zooming in a PDF.** The text of a page can be selected with the pointer and copied. **Find in document** searches the whole document, without regard to upper and lower case and across the ends of lines, marks what it finds and steps from one match to the next (Enter, Shift+Enter, or Cmd/Ctrl+G). The pages can be made larger and smaller, from 25% to 500%, or fitted to the width of the pane; they are drawn for the screen's own pixels, and again when the pane changes its width. A PDF made on a Mac often writes common Chinese characters as look-alike radical signs: finding and copying take those as the characters they stand for. Links, forms, annotations and scripts in a PDF stay off, and the reader neither prints nor edits. Its texts follow the app's language.
- **An Agent's answer as a tab.** The Markdown and PDF buttons under an Agent's answer open the answer in the reader's tabs, where they used to save a file at once. Such a tab has the button **Save a copy**. Both buttons have new icons.
- **Room information on one page.** The room information panel had two tabs, and the only way to remove someone was a button in that member's profile, hidden from anyone who may not remove. The panel is now one page. Its members are a grid of avatars with names. A tile with a plus, shown to every member, offers to invite people or to add one of your Agents. A tile with a minus is shown only to someone who may remove at least one member; in a room created in Hagency that is the room's creator. It marks the members who can be removed, and a tap on a marked member asks for confirmation before anything is sent. Who can be removed follows the room's power levels. The Hagency service is never offered, because the room's Agents are invited through it.
- **The room by its name, and renaming it.** The page shows the room's name where it showed the room's Matrix ID. Whoever may change the name, by the room's power levels, opens a field from that row and saves the new name; anyone else is told that only the room's administrators can change it. The topic has a row only in a room that has one.
- **A nickname of your own in a room.** The row **My nickname in this room** sets the name the room's other members see for you in that room alone; an empty field returns to the name of your account. When the account's name is changed later, the homeserver copies it into every room, and the nickname is replaced.
- **Your own Agents in a room.** The row that lists the viewer's Agents in the room (in Chinese now "我在此房间的 Agent") names pool Agents as well as personal ones, each pool Agent with a line that says it runs on a shared resource pool. A room in which the viewer has no Agent does not show the row.
- **A room's history beside the room list.** On a desktop the history of a room (search, media and files) opened over the whole window. It now opens inside the room, under the header and over the chat only: the room list stays in use, the room's information panel opens beside the history, and a member's profile on top of that. A room that is not open, a thread, and a phone still open the history over the whole window.
- **Member lists follow a removal.** Where a homeserver left a changed membership out of what it sends, someone removed, banned or invited by another member stayed unchanged in the member lists of the others, although their timelines showed the change. The room information panel and the invite dialog now ask the homeserver for the full list of members each time they load, and use the stored list only when it cannot be asked. The open chat's own list, the one that offers names after an @, follows.
- **Moments inside the chat window.** On a desktop, Moments opened in a window of its own or as a dialog over the chat. It now opens in the chat pane, in the single-chat and the tabbed layout, with the room list and the navigation still in reach. Closing Moments or choosing a chat brings the conversation back. Moments is not written into the saved layout, so the app starts again with the chat that was open.
- **No card for a run that completed.** A run card stays under the message that started an Agent's run. Once the run had completed, the card said only that it was completed, like a message of its own, while the result is the Agent's reply in the thread. Such a card is no longer shown. It stays for as long as the completed run still holds an instruction of the person's: one being written, sent or tried again, or one left unexecuted or unconfirmed. The cards of running, stopping, stopped, failed and unknown runs are as before.

**New in rc.14**

- **One computer hosts Agents for several accounts.** The hosting service of a computer served one account. It now serves every account that sets up hosting on that computer, accounts of different servers included. Each account has its own sign-in for hosting, its own work folders and its own state: pausing, resuming or stopping hosting, and signing out, act on the account they are done for, and the others keep running. A set-up made by an earlier build stays where it is. Uninstalling the service still ends hosting for every account of that computer's user. On the command line, `daemon pause`, `daemon resume` and `daemon sign-out` take `--server` and `--owner`, and need them once more than one account hosts. The rules are in `docs/adr/0012-owner-daemon-shared-dashboard.md`.
- **My Agents on a server without resource pools.** Where the server offers no resource pools, the page hid the list of personal Agents and the button that creates the first local Agent, so an owner who had set up hosting found no way to an Agent. Both are shown again.
- **A restored chat that is no longer there stops loading.** A room or thread tab restored at start waited without end when its room had gone from the server or arrived late. After ten seconds the tab offers Retry and Close. A refusal that arrives later (not a member, no such room) is still shown, and leaving a room or being banned from it during the first synchronisation reaches the tabs that are open.
- **Room information is read again when its panel comes back.** The narrow and the wide layout each keep their own room information panel, and a panel shown again used the member list it had read earlier: on Windows one layout showed four members of a room and the other two. A panel now reads the members again when it becomes visible, and an Agent picker left open in a panel closes when that panel is hidden.
- **The device ID stays on the account page.** **Settings → Account → This device** shows the full ID of this device, with a copy button, before and after verification. It used to stand only in the banner of an unverified device and went away with it.
- **Connecting a local Codex on Windows.** The connection could fail in several places: `codex.exe` was not found through `PATH`, the Codex profile folder of the Windows user was not used, the check started Codex in a folder whose path was too long, and the path of the instructions file was compared in a spelling Windows does not always use. These are corrected. A check that is cancelled no longer leaves an empty folder behind. The user's Codex configuration is not changed.
- **Codex sign-in says to finish in the browser.** While it waits, the Coding Tools sign-in sheet says that the authorization is completed in the browser and offers **Reopen authorization page**. Once the sign-in is confirmed, the heading reads **Codex connected**.
- **Why a refused tool shows no approval.** With a tool rule set to Deny, a local Agent's request is refused at once and nobody is asked, while Codex reported it as "rejected by user". The Limits panel now says so, in English and Chinese, and the refusal is written to the diagnostic record of declined requests.
- **Account folders on macOS are private from the start.** Signing in for management only, before hosting was set up, could create the folder that holds the computer's account registry so that other users of the Mac could read it. It is now created private, and an existing folder with wider permissions is corrected when it is next used. A folder that is a symbolic link, that others can write to, or that carries an access list granting access, is refused instead of corrected.

**New in rc.13**

- **Pooled Claude Agents in a container, pool by pool.** In **Agent → Hosting**, the page of each Claude resource has the switch "Run this resource's Agents in containers". With it on, every run of that pool's Agents gets a fresh container of the Mac's Docker-compatible engine (Docker Desktop, OrbStack, Colima or Podman), removed when the run ends. The container sees only the room's own folder and, where the space has one, the shared project folder; its system files are read-only, and it runs as the owner's user without added privileges. Turning the switch on builds the image when the engine does not have it yet, which downloads a base image and Claude Code and takes minutes the first time. A change applies from the next run, and a member's conversation with the Agent starts anew when the pool changes between the sandbox and a container. Codex and Octos pools, local Agents and personal Agents are unchanged and have no such switch. The design and its rules are in `docs/adr/0015-pooled-claude-containers.md`.
- **What the container does not protect against.** Claude Code's own tool sandbox on Linux needs two of the engine's default restrictions lifted in the container (seccomp and masked system paths), which widens what a member's commands can reach toward the engine's virtual machine; with Docker Desktop that machine shares the Mac's `/Users` folder. While a run's container exists, the owner's own account can read the run's credential from the engine. The engine's optional TCP endpoint without TLS must stay off. A model endpoint on the Mac's loopback address is refused for a pool that runs in containers.
- **When the container cannot be used.** If the saved choice cannot be read, every pooled Claude run on that Mac is refused (`shared_claude_container_invalid`) rather than run in the sandbox against the owner's choice; turning the switch off for any resource removes the saved choice. A container that does not start refuses that run with `shared_claude_container_unavailable`.
- **Hosting's management store, once shut down, counts as closed at once.** For a moment after it had confirmed its shutdown, a check that depends on it could still find it open.

**New in rc.12**

- **Sending does not wait on the diagnostic log.** The app wrote its diagnostic output directly, so a log reader that stopped reading could hold up the workers that send messages. The output now goes through a bounded writer that drops lines when it is full. In a development start on macOS the app also keeps running when the launcher's log reader stops or goes away.
- **A message that was not handed over can be restored.** A message stays pending in the composer until the send queue has accepted it; from there the timeline reports its delivery as before. When the handover fails, the sender can put the exact draft back, with its mentions, its reply context and its signing choice, in the room or thread it was written in. Restoring needs an empty composer, and sending it is a separate step. After an interrupted handover the app asks the sender to look at the conversation before sending again. A draft to restore is kept in memory only, until the app is closed.
- **Message text is not written to the diagnostic log.** Diagnostic lines that contained the content of outgoing messages, signed text or verification details are removed.
- **Adding or switching an account.** Adding an account could empty the room list and still show the previous account's open tab, its messages and its chat information. The previous account's workspace is now closed before the change is confirmed, and the new one is built from the new sign-in: saved room and space tabs come back only where that account is a member, and a late result for the previous account is dropped. Room information that stayed on "loading" after this device was verified is asked for again; the request ends after 30 seconds and offers a retry.
- **Browser sign-in on Windows when an account folder has wider permissions.** A browser sign-in could succeed and still return to the sign-in page with `credential_storage_failed`, when an earlier account folder or its history list had inherited wider permissions. After the account and device are confirmed, the Desktop now repairs the permissions of the current user's own files and checks them again. A history list it cannot read or confirm is set aside under another name, and the chat databases it named are left untouched.
- **The TSP badge covers the content that is shown.** TSP signing is an optional part of the build. Where it is on, the green badge now needs a signature from the sender's known identity that agrees with the type and content of the message as displayed. An edit without its own signature does not take over the badge of the original.
- **Layout.** The Agent badge sits level with the sender's name. On the account settings page the verification banners and the encryption recovery section share one column that follows the width of the pane, and wrapped tabs and buttons have space between their rows.

**New in rc.11**

- **A local Agent keeps its role in a room.** In a room of an Agent space every top-level message starts a new conversation, and a local Agent began each one without the role a person had given it before. A local Codex, Claude Code or Octos Agent now saves a role, or standing instructions, that it is given for a room. They are kept, encrypted, on the computer that runs the Agent and stand at the start of every conversation in that room and of a timer's turn there. What the Agent's owner gives applies to everyone in the room; what another member gives applies to that member's own conversations. Telling the Agent that the role has ended removes it. Pooled Agents do not have this, another Agent in the room does not see the role, and no page shows or edits it.
- **Browser sign-in on Windows computers that could not save it.** Before it saves a sign-in the Desktop checks the folder that will hold it. On some Windows computers that check refused an ordinary local NTFS disk because of one device flag it did not know, and browser sign-in failed. The flag is now accepted when the folder is on a fixed local disk; the other checks are unchanged. A first start that was interrupted is also confirmed on disk before its installation marker is used again.
- **Signing in again when the saved key is missing.** When the key of a saved sign-in was no longer in the system's credential store, a new browser sign-in ended with `credential_missing` although Pasion had accepted it. The Desktop now completes the sign-in with a new local database and says so in a notice. The earlier sign-in file is kept under another name and its chat database is left untouched; those earlier chats stay closed on this device until their key is back.
- **Sign-in errors that say what to do.** When the system's credential store is locked, refuses access, cannot be confirmed, or, on Windows, cannot take another entry, the sign-in page names the cause and the next step, in English and Chinese, where it used to show a code.

**New in rc.10**

- **Timers for local Agents.** A local Codex, Claude Code or Octos Agent can set itself a timer in a conversation, once or repeating ("remind me in an hour", "check the build every ten minutes"). The computer that runs the Agent keeps the timer, so it survives a restart of the app or of that computer's hosting. When it is due the Agent runs a turn and posts the result in the conversation where the timer was set. Nobody is asked to approve the turn itself, and its tools follow the Agent's tool rules as in any turn; the Agent's budget, a rule that denies its requests and stopping the Agent still apply. A conversation holds at most 8 timers, and a repeating one ends by itself after 200 runs or a week. Pooled Agents have no timers yet.
- **A local Claude Agent's own turns reach the room.** Claude Code can start a turn by itself: a timer of its own fires, or another Claude Code session on the same computer sends it a message. The output of such a turn used to be thrown away. It is now charged like any other turn and posted to the conversation the Agent answered last. A message from another session does not carry the room's trust: in that turn the owner is asked for every tool, and the request says where the message came from.
- **A card for a turn nobody asked for.** While such a turn or a timer's turn runs, the message it belongs to shows a run card. The person who sent that message, or the owner, can stop the turn there; stopping the turn of a repeating timer ends the timer too. A question the Agent asks in that turn goes to the same two people. Instructions cannot be added to such a turn from the card.
- **Agent reports are kept until they are delivered.** A message an Agent produces has its own identity and waits in an encrypted local store, so it can still be delivered after the run that produced it has ended or the app has restarted. A send whose outcome is unknown is checked against the room before anything is sent again, so a report is not posted twice.
- **Local Codex Agents on Codex 0.169.** Reading the room's history and receiving or sending files failed for every local Codex Agent once Codex 0.169 was installed. They work again.
- **Adding a new local Agent to a room of an Agent space.** "Add agent" failed for every local Agent created recently, with only a generic message. The Desktop now makes the Agent available to rooms and adds it.
- **Local Agents keep running after a sleep or a network loss.** After the Mac slept, all of its local Agents stayed down until hosting was restarted, while their pages still showed them as started. Their services now keep trying, with growing pauses, until the sign-in is renewed.
- **Octos pools from the Desktop.** An owner can publish, amend and renew an Octos pool in the Desktop. A pooled Octos Agent's tool requests go to the person who sent the message, as for Codex and Claude. A local Octos Agent has a shell, which follows the Agent's tool rules.
- **Pooled runs.** An answer is no longer lost when a second message arrives while the first is being answered. A message sent to a busy Agent keeps its context, a stopped run is shown as stopped, and long room histories are read page by page.
- **Tool requests of local Agents across the app.** A local Agent's tool request shows in the app-wide alert, in the counts and on the message that caused it, not only on the Agent's page. A room or a member that has no tool rules of its own follows the Agent's rules, and resetting a level clears it. Folder access for local Claude Code and Octos Agents works.

**New in rc.9**

- **A shared project folder for an Agent space.** The Agent space form has a "Shared project folder" switch and a folder name. With it on, the coding Agents of that space that run on one computer work in that one folder, so different Agents can work on the same project. This covers pooled Codex, Claude and Octos Agents and that computer's local Codex and Claude Agents. The folder is made under `~/Hagency Projects` on the computer that runs them, and an existing folder is never taken over. Spaces created without the switch behave as before. Local Octos Agents keep their own folder for now.
- **No more unencrypted messages into encrypted rooms.** Before, a room whose first state events had not reached this device was taken as unencrypted for good. This was seen with rooms the device had just created. Messages to such a room were sent without end-to-end encryption, and the composer showed the unencrypted placeholder. Now, before the first send in a session to a room taken as unencrypted, the app asks the server. If the room is encrypted, the app corrects its record and its members' devices get the room key. If the server cannot be asked, nothing is sent and the sender is told to try again. Rooms taken as unencrypted are also checked when they are first listed. Such a room can still show a name made from its members, and its space can list no rooms, on the device that created it.
- **Pooled launches that fail after their claim recover.** A pooled Agent whose launch was claimed but never started no longer stays "Stopping" for good. After the usual grace, the hosting daemon records that launch as stopped, so the next message can run. A start with less than 12 seconds of its window left is declined before it is claimed, so its message runs again instead of failing.
- **Claude pool grants on another Claude account.** After the owner signed Claude Code in to another account, publishing, amending or renewing a Claude pool used to fail without a message; adding people to a pool's list was where it showed. It works again.
- **Thread previews.** A thread under a message an Agent answered shows its run card as "Agent run record" and a question as "Question from the Agent". Before, it showed internal debug text or a "running" state that no longer applied. Four texts on the local Agent pages are now translated in the Chinese interface.

**New in rc.8**

- **Octos coding pools.** An owner can publish an Octos profile as a pooled coding resource and choose one of its configured models, local and custom endpoints included. Questions, steering, tool approvals, confined coding tools and usage go over OUP, and each shared run gets its own scoped Octos process. Octos tool requests stay with the owner. The shared Octos runtime is macOS-only.
- **Progress in the room.** During a run, Codex commentary and Claude's messages between tool calls arrive as separate room messages before the final answer. Each one is kept in an encrypted local outbox and retried under the same Matrix transaction, so a lost reply does not post it twice.
- **The sender answers a pooled Agent's tool requests.** The request's details go only to the devices of the person who sent the message, and only their decision counts; the resource owner is neither asked nor shown that conversation. A pooled Codex request outside the Agent's work folder is refused at once. A request nobody answers does not run, and the Agent is told that nobody refused it, so it can ask again.
- **Claude pools run on whichever Claude account the owner is signed in to.** Signing Claude Code in to another account no longer stops the pool's launches.
- **Full trust for local Agents.** A local Agent's high-risk tools can be set to full trust. For the owner's own messages the Agent then runs commands, changes files and uses the network on that computer without asking, and outside its work folder. Another room member gets it only where the owner also sets full trust for that room and for that member. The Agent's web search switch now applies to Claude Code too.
- **The Hagency panel opens without the permission sheet.** Local Agents are offered only on the computer that runs the account's Agents; a local Agent seen elsewhere says why it cannot run there.
- **Approval cards** show a decision at once ("Sending: Approve once…", then "Approved once. Waiting for the Agent to continue."), mark the next request as a new one, and describe a request as "<Agent> wants to use Bash" with its command or file instead of JSON.
- **Avatars.** A new avatar can be cropped, by dragging and zooming, before it is set. It then shows in the profile icon and in Settings, and so does an avatar or name changed on another device. A clicked button no longer stays pale.
- **Agent runs.** Input added while Codex is answering no longer ends the run as interrupted. The owner's `/clear` and `/compact` reach a local Claude Agent. A pooled Claude run card asks again for a device that was not ready, so Stop and added instructions keep working on long runs.
- **Pools and administration.** The Claude pool form lists the models the owner's own Claude Code offers. The server administrator's admission requests are grouped by state with a filter, and a new request turns the Agent tab red.
- **Chat and account.** An image pasted into the composer becomes an attachment through the same preview as a picked file. Reading back and forth through a chat no longer builds each message again. Settings → Account can reset the account's encryption identity from this device, behind a warning; the server confirms it with the account password.
- **For developers.** The owner daemon and the unit tests run under the JIT runner too: see the README's "JIT mode" section and `.jit/NOTES.md`.

**Fixed in rc.7**

- The macOS app finds the files packed inside it. In the rc.6 macOS installer the sign-in logo, icons and other images were missing and text was drawn in system fonts instead of the bundled ones, on every Mac except the one that built it: the package was built with a resource folder setting that the new engine does not use. The Windows installer of rc.6 was not affected. The automated installer check now fails a package that does not draw its bundled logo.

**New in rc.6**

- Claude Code Agents. A resource owner can run a local Claude Agent, or publish a pool from "Claude Code on this computer". The pool uses the owner's own Claude Code configuration, read at each launch: an API key, a custom endpoint token (for other models behind a compatible endpoint), or the owner's claude.ai sign-in. **Anthropic's consumer terms do not allow making an account available to other people; putting a claude.ai subscription sign-in behind a shared pool is the owner's own decision and risk.** An API key under the owner's own agreement does not have that problem.
- Shared Claude runs are confined to the Agent's own work folder for writes and can reach the network. An owner can give a Claude Code pool or a pooled Claude Agent full trust; tools, shell commands included, then run without asking the owner.
- Local Agents work beside pools. An owner's local Codex, Claude Code or Octos Agent can be added to a room, and other members of that room can call it. Tool rules can be set per room and per member, down to asking the owner for every tool call.
- A message sent while a Claude turn is running joins that turn, as it already did for Codex. The owner's own message that starts with `/` reaches their local Claude Agent as a slash command. A shared turn ends after one hour.
- The run panel shows the live answer formatted and lets it be selected. The owner's usage report lists each pooled Claude call.
- Coding Tools lists Claude Code and is laid out as grouped lists. A pool whose server connection is closed can be deleted, and an owner can publish a further pool of the same Claude model. A person picked for a pool's list keeps the exact account name the server returned, capital letters included; before, such a name was lower-cased and publishing failed with "An account on the list no longer exists".
- Runs are harder to lose: a turn survives one unanswered validity check or a brief authority failure, a run that starts during a token refresh is no longer ended, Stop on a Codex run no longer leaves the Agent silent, hosting can be resumed after a stop, and the macOS owner daemon no longer runs as a low-priority background job.
- Chat: your own messages sit on the right with your avatar at the edge, the chat column has wider side padding, the room list snaps fully shut when its divider is dragged to the edge, and mini-app buttons and sliders keep their shape. A restored thread tab no longer stays on "Waiting for this room to be loaded", and open rooms let the window go idle again.
- Chinese and other composing input methods work on the new engine: a committed word is no longer overwritten by the next one.
- From the main line since rc.5: Matrix links open rooms and threads in the app, device verification and recovery, Space filters, reactions and moderation, bounded attachment downloads and chat caches, lower idle CPU and memory, explicitly authorized shared workspaces for local Agents, and a first-time path from sign-in to the Agent page.

**Retained from earlier release candidates**

- Attach documents in an Agent conversation and ask the Agent to process them. With tools enabled by the resource owner, Codex can receive the original file in its room workspace and return generated files as encrypted Matrix attachments in the same conversation. Each file is limited to 8 MiB. Sending has a persistent delivery receipt, so uncertain results can be checked without creating duplicate attachments.
- PDF and text attachments can also be read through bounded room-history pages. Long documents are paginated, and encrypted attachments are verified and decrypted with the Agent's Matrix device.
- Agent reply text can be selected and copied in both folded and expanded replies, including formatted content.
- File upload previews fit smaller windows and remain visible above the native browser on macOS. Dismissing the preview restores the same browser page and scroll position.
- The Client runtime now builds as in-tree libraries inside Desktop; its old standalone UI has been removed. Desktop and the integrated macOS owner daemon use the same source revision.

- Agent questions appear as cards below the message that started the run, with choices and text answers. A message can show questions from several Agents. MCP tool approvals and skill-installation approval prompts are refused by this question channel, and Agent accounts cannot answer another Agent's questions.
- Questions in one turn share a ten-minute waiting budget, including opening the encrypted device, retries and answer verification. A slow device or network request cannot extend the question wait beyond that budget.
- Question cards recover their final state after hosting restarts or interrupted requests. An answer is shown as accepted only after it has been delivered back to the running Agent; unanswered cards expire locally even while the network is stalled.
- Desktop retries encrypted cards that could not initially be decrypted when room or device keys arrive. Successful retries appear immediately, and signing out prevents an older account session from updating the current session's cards.
- Long Codex turns stay active while tools are working, and a completed turn's answer is retained when a command is still running.
- Hosting is managed inside **Agent → Hosting**. Desktop and its background daemon use one registered owner resource directory per account on each computer. The daemon can keep the resource pool available after Desktop quits. The separate Hagency Hosting installer is no longer needed.
- Interrupted Agent calls no longer occupy the entire remaining allowance. All Agents count known consumption instead of the call's reservation. A call whose process is confirmed stopped closes at its known consumption, and later usage reports can still add to that amount. **Missing usage counts as zero, so the ledger can understate provider usage and a run can exceed its allowance.**
- A shared message whose previous attempt is proven never to have started can be retried automatically, up to three times, on servers advertising `shared-demand-retry-v1`. Retries retain the same message and queue position. A lost acknowledgement is reconciled through the original request; an attempt that may have executed is not automatically run again. Older servers keep the evidence-only recovery behavior.
- Running Agents have bounded retries for transient authorization checks and can retry an activity renewal with its original request ID. Revocation ends the run immediately. More precise diagnostics distinguish failed authorization stages; these changes do not establish credential refresh as the cause of every interrupted run.
- Background hosting raises its macOS open-file limit, prioritizes unfinished message recovery, bounds provider-report refresh and shutdown, and reuses Agent device credentials across restarts to avoid unnecessary Matrix logins.
- Encrypted room history retains bounded pagination, event deduplication, long-message handling and malformed-event recovery. Codex controls when to compact a room-history thread. The Windows WebView2 reader, window-focus and divider improvements from rc.2 remain included.
