# Next Hagency management mini-app slices

Reviewed 2026-10-16 against the original JavaScript console, restored Rust console/domain code, current owner engine, and [parity inventory](hagency-management-parity.json). This is an implementation checklist, not an acceptance report. The inventory has 104 retained-native, 189 JavaScript and 70 owner-engine entries; these overlap and are not 363 independent features. Existing Rust methods do not establish mini-app parity.

The current feature-by-feature status is in the [104-operation family matrix](hagency-management-feature-matrix.md). It distinguishes implemented source, read-only views, missing original behavior and unverified full flows, with evidence. This older detailed design remains useful for protocol gaps, but its individual “missing” descriptions below are historical plans rather than the current delivery checklist. In particular resource detail, agent admission/status, coordinator allocation, work history and cleanup now have typed host/UI implementations; their actual acceptance limits are recorded in the matrix.

A project request's approved state remains permission to proceed, not a reservation, Matrix project or runnable agent. Requested tokens are monthly intent; actual native grants bind their exact accounting period.

**Blocking protocol issue before editing an admitted resource:** `resource_publication_revision` hashes the complete resource, including publication. Editing or toggling publication changes the native revision. Central `verify` and `resume` require the old pinned revision, while `management_contributions` has a permanent unique `(owner, device, resource)` key and `create_management_contribution` rejects a second record, including after revocation. There is currently no working re-admission path for that changed resource. Add a versioned amendment/re-admission transition that retains history, invalidates verification, identifies affected requests/grants, and requires the appropriate decision; or initially permit edits only on resources never contributed. Do not expose a button whose only recovery path cannot succeed.

Original resource fields needing explicit reconciliation: per-day rate cap (`rateCapPerDay`), resource-level execution policy, shared seat declaration and role-offer publication/count/tier limits. `CeilingChange` currently represents preserve/clear/monthly tokens; it does not carry the original daily cap. Original `mockup/app/resources/new/page.jsx` and `components/ExecutionPermissions.jsx` supply these controls. Do not silently drop their values or advertise unimplemented enforcement.

## 2. Approved project → allocated and usable project

This is the next complete workflow, ahead of presenting agent creation as finished:

1. Project manager submits the project request; designated server administrator decides it.
2. Resource coordinator reviews actual resource headroom and eligible managers, selects an explicit amount/period, and submits allocation.
3. The enrolled executor reserves capacity in the existing native ledger and returns its durable receipt. Display `Awaiting executor`, `Reserved`, refusal, or unknown outcome distinctly.
4. Create or adopt the Matrix project/rooms with verified ownership and membership. Display room-setup progress and recover an interrupted creation using its original ID.
5. Mark the project ready only after reservation and Matrix readiness are both acknowledged; then enable its agent flow.

Native building blocks already exist: `contribute_resource`/`put_coordinator_resource`, `server_engagement_resources`, `approve_coordinator_project`, `begin_project_setup`/`validate_project_setup`/`finish_project_setup`, `coordinator_project_ready` and `verify_coordinator_project`. They require configured coordinator authority, current delegation/registration and verified Matrix evidence; they are not arbitrary commands a mini app may construct. The personal owner engine separately has `Command::CreateMatrix`, `AdoptProject`, `AdoptRoom`, `Creations`, `Creation` and `ResumeCreation`.

Central source now links the project plan, explicit parent grant, coordinator authority, reservation command/result, executor generation, setup and revocation state. Separate schema-10/11 work adds Matrix identity and bounded runtime qualification contracts. These have isolated PostgreSQL/HTTP coverage; the local fixture enables only setup readiness and administrator assignment. Remaining integration is native source adoption and owner consent, grant publication, enabled allocation delivery, actual Matrix setup and provider execution through one complete mini-app flow. A personal owner-engine project or an old coordinator grant cannot simply be relabeled as this approved project plan. Native allocation and command receipts must remain the single capacity authority.

## 4. Usage, activity and work

- **Usage:** `Resource → allocations → project → agent` with `available / total`, reserved unused, known consumed, period and last observation. Use `resource_budget`, `usage_report`, `usage_totals`, `side_budget`, `server_engagement_resources` and `coordinator_agent_usage`; extract bounded owner/coordinator/project-manager projections. Current catalog has no total/available capacity. Do not convert missing observations to zero, count active allocations as measured usage, or conflate cache-read tokens with fresh token draw. Preserve incomplete/attributed usage and final settlement evidence. Original `mockup/app/usage/page.jsx` and `workforce/page.jsx`; `MGT-099–101`.
- **Work board:** preserve task list/filter/detail, create/edit, assignment/acceptance, transition, comments, delete and per-agent/project views. Native `operator_tasks`, `operator_task`, `create_operator_task`, `update_operator_task`, `transition_operator_task`, `comment_operator_task`, `delete_operator_task`, `operator_project_board` exist. Their old console authority is broad local operator authority, not a Matrix project-manager grant: define project/assignee visibility and mutation scopes before wiring the mini app. `MGT-089–098`.
- **Task graphs:** preserve graph creation, dependency visualization, status/result, node updates and cancellation. The retained console graph document/dispatch code in `console/graphs.rs` is distinct from store `create_workflow`/`runner_workflow`/`cancel_workflow`; do not substitute one based on similar names. Extract the retained service and its durable root-node dispatch behavior or document/verify an explicit migration. `MGT-045–049`, `JS-149–154`.
- **Activity and attention:** preserve delivery events, message inspection/suppression, alerts/triage, pending Matrix invites and connection diagnostics. Reuse the durable Inbox and central outbox for assigned actions, with account-scoped deep links to current objects. Notifications/reminders, background delivery and delivery failure visibility remain separate implementation work; the mini app does not need to stay open.
