## Next retained editor checkpoint: local resource names

The current original-source audit distinguishes three different fields. The
JavaScript preset has an operator-selected `name`
(`hagency/mockup/app/resources/new/page.jsx`, POST `framework-presets`). Native
`Resource` currently has no corresponding name; its model is not a name and its
capabilities are derived from qualification. Central contribution `label` is
the published association name, and the server has no rename/amendment endpoint.
The original daily rate cap and execution permissions also remain distinct from
the current Rust monthly token ceiling.

The proposed first editor therefore changes **local display metadata only**. It
must not reinterpret the legacy `ConfigureResource` call as an adopted-resource
writer or change the published contribution label. The closed native operation
is `resources.rename {commandId, id, expectedNameRevision, name}`: bounded Unicode
single-line text, optional clearing via empty name, original native command
custody, and exact independent name-revision CAS. List/detail show the name with
the canonical resource ID; admission/grant/project context keeps its original
published label. The review explicitly identifies the change as local.

Implementation is planned in a separate native metadata table, with name and
its own monotonically increasing revision; it is excluded from the effective
resource-definition hash, original grant receipts and provider/seat identity.
An effect receipt commits with the metadata under current original
profile/installation authority. Lost replies recover the original receipt;
stale revisions do not overwrite a newer name. A read or rename cannot create a
resource, change model/capabilities/limits, allocate capacity, or release a hold.

The first writer will require the active canonical adopted backing. Legacy
sources remain descriptive/read-only until their exact metadata can be adopted;
no new metadata is written into a fenced original ledger. Native schema83/file085
is reserved for this slice, after the peer-owned schema82 start-intent migration.
No metadata migration or editor production code has been activated at this
planning checkpoint. Startup-failure handling is being completed first.

Required acceptance includes same-model resource disambiguation, original-ID
replay after restart/lost reply, concurrent rename CAS, wrong profile/device or
retired package denial, and proof that resource configuration, budget/seat,
grant and contribution identities remain byte-for-byte unchanged. The full
model/limit/amendment and resource-definition parity gaps below remain open;
local naming does not establish those original operations as accepted.

The next mini-app screen can read a native resource now. Configuration editing
remains unavailable until native provenance proves the resource has never been
offered. This is a deliberate contract boundary, not a UI role inference.

## Read contract implemented in this checkpoint

`hagency.resources.get` accepts only `{id}` and requires `ReadResources`. It
returns a bounded `ResourceDetail` from one SQLite read snapshot: the existing
resource summary and revision, configured ceiling, native model/reasoning
qualification choices, model tier, and observation time. Provider identity,
seat references, credentials, private paths and login URLs are excluded.

In the running42 build, `editing.allowed` is always false with
`contribution_history_not_proven`; isolated43 eligibility is described above.
The bundle detail screen requests only this read grant and uses the existing
Hagency section/detail components:

1. Resource model, reasoning, framework and derived capabilities.
2. Native remaining/total budget, committed/reserved amounts, configured period,
   usage observation and its evidence. Missing usage or limits remain unknown.
3. Local publication status, clearly separate from central admission.
4. A read-only explanation and connection navigation. Refresh retains the exact
   resource ID; vanished resources show unavailable rather than cached editable
   data. Qualified model choices do not prove provider execution readiness.

Evidence: client `management/resource_detail.rs`, `domain/resource_detail.rs`,
`console/native/management.rs`; Desktop `src/host/hagency/resources.rs`.

## Why existing configuration is not safe to expose

Native `ConfigureResource` already retains command identity and checks expected
revision, provider association and current writer authority. Its shape also
allows creating a derived configuration and changing a legacy engagement; those
are wider than this requested editor.

It does not establish that a resource was never contributed. Central
`management_contributions` permanently identifies owner/device/resource and pins
its resource revision. Editing changes that revision, while no amendment route
exists. Revocation does not remove the original record. Paginated absence,
acknowledged/scrubbed intents, a different homeserver/profile or a lost private
journal cannot establish negative history.

Evidence: client `domain/resource_configuration.rs` and
`management/intents.rs`; server `management.rs::create_contribution`,
`verify_contribution`, `resume_contribution`.

## Required native provenance before editing

Add a canonical registry-owned provenance record created atomically with each
new qualified resource: exact installation/resource identity, original creation
receipt digest and an irreversible offer-attempt fence. Imported or pre-existing
resources start as `history_unknown`, never as `never_offered` merely because
local records are absent. This depends on complete source adoption and writer
exclusion; it must cover all profiles and homeservers sharing that resource.

Every admission path must atomically record the first attempted offer and exact
resource revision before HTTP. Rejection, revocation, acknowledgement, retirement
and lost responses never clear that fence. The configuration writer must check
`never_offered`, current resource CAS, original provider/resource binding and
absence of incompatible holds inside its transaction. Native consent/retry
continues using its original command; no browser-supplied eligibility boolean.

Only then add a closed edit request with model/reasoning selection and supported
limit changes. It must force `create=false`, forbid engagement changes and keep
original-command recovery. A concurrent offer either sees the edited revision
or permanently fences the edit before its write.

For previously offered resources, a separate central amendment protocol must
retain the contribution ID/history, pin old/new definitions, invalidate stale
verification and fence affected allocation/executor authority before re-admission.
It must handle retained liabilities; local unpublication is not server withdrawal.

## Preserved parity gaps

The original web editor (`mockup/app/resources/new/page.jsx`) includes a daily
rate cap and execution permissions. Current Rust `Resource`/`Ceiling` represents
tokens and period only, and `ConfigureResource` supports preserve/clear/monthly.
This read projection does not invent or claim support for omitted fields. A
future editor must add explicit storage/enforcement and migration before offering
those controls. Resource templates, deletion, account retirement and contribution
amendment are separate flows; none is a shortcut around this guard.

Remaining identity UX: different native configurations can currently render the
same model/framework and budget (the owner test profile has two such cards).
The instrument probe may select an explicit public ordinal, but that does not
make the resource's identity discoverable to a person. A later list/detail
projection should supply an authoritative resource label and, where visible,
its connection/project context. Do not infer a name from private provider
identity or claim an ordinal independently verifies the underlying resource ID.
