# Additional resource configurations

Checkpoint45 is qualified, promoted locally and running in all four original
role sessions. Its source and evidence are retained in `.run/management45-stage`. This is the retained native console's `POST /api/resources`
operation, distinct from editing a never-offered resource and from amending an
admitted contribution. Its closed Desktop service, native confirmation and EN/CN
mini-app flow are implemented and qualified. Promotion and all original-session
activations pass, as does the read-only original-settlement regression. Their
receipts remain separate from the new configuration fixture.

## Original behavior retained

The request selects `sourceResourceId`, its exact `expectedRevision`, a qualified
model/reasoning change or preservation, and a resource ceiling change or
preservation. The native host supplies durable `commandId` custody. A successful
operation creates a native-generated configuration ID while preserving the
source's framework, provider, actual private account association and shared
seat. The source is unchanged, including when published or previously offered.

As in the original console, the new configuration is locally published. That
flag does not constitute a server contribution, admission, capacity grant,
delegation or allocation. Those existing flows still require their own actions.
The native review must explain this distinction. It must not reuse an in-place
edit review that implies the original resource will change.

The monthly resource ceiling can be preserved, set (including zero), or cleared.
Clearing means unknown resource headroom. It does not imply unlimited account
capacity. The transaction never writes seats, provider quota identity,
allocations, holds, usage, namespace credentials or an account declaration.
Capabilities remain derived from the qualified model profile.

Creating a configuration uses the same static qualification as the retained
console and does not launch a provider or claim fresh provider authentication.
Original private binding and managed-account state are still checked. Execution
and contribution retain their existing provider verification requirements.

## Canonical transaction and recovery

`CreateResourceConfiguration` is a closed operation. No caller-supplied account,
seat, provider, filesystem path, publication flag, engagement or quota can enter
its input. Only the trusted native confirmation path can supply a finite
confirmation deadline and current SDK/package authority.

One immediate transaction authorizes current source access, recovers an exact
original receipt, compares the source revision, validates the resulting model,
checks original private custody, and creates the new resource. Managed namespace
configurations retain the exact account, generation and owning profile; ordinary
private associations retain their original account/generation. The new resource
is granted only to the requesting profile. Other profiles' source grants do not
automatically expose the new configuration.

The resource, association, profile grant, immutable creation provenance and
original operation receipt commit together. Any failure rolls them all back.
The original account/quota and source definition are unchanged. An occupied
original owner command cannot be reused for a different effect. Replays recover
before mutable source/model/account checks; current authorization remains
mandatory. Private reply loss and native restart retain the original command.
A source CAS failure after an absent original receipt has its own
`management_resource_source_changed` code. A fresh failed request records a known
no-effect reply so the UI can refresh the source. Command collisions, scope loss
and uncertain outcomes remain distinct and do not imply non-application.

The first native process test initializes an isolated installation using the
real first-use API, creates a synthetic local source, exercises read-only review
and creation, deliberately omits a private reply after the canonical commit,
restarts `NativeOwner`, and recovers through the public saved-command API. This
is native workflow testing, not actual Desktop UI or real provider evidence.

## Desktop integration and observed acceptance

`hagency.resources.create` is a separate closed capability. Resource details
opens an independent creation draft; editing an existing configuration retains
its own draft and restrictions. Source ID/revision, qualified model/reasoning,
new resource ceiling and the unchanged shared account limit are visible before
native confirmation. Generic service dispatch refuses an unconfirmed creation.
Success opens the new resource's ID. Local publication is explicitly separate
from server admission and allocation; creation does not verify provider login.

The native review expires after five minutes. Accept passes the earlier of that
expiry and now plus30 seconds to the canonical writer. Recovery uses the saved
original command and exact input; a recorded result is reviewed as recovery,
not a new configuration. Current source access and package/session authority
remain mandatory. A known pre-effect source revision failure can be refreshed;
command collisions and uncertain outcomes keep original request custody.

`.run/management45-stage/create-ui-build-v1` binds the paired source, release
binary,50 host checks,11 confirmation-layout checks and actual hidden Metal
windows. Creation VM checks46, existing editor regression42, both full-bundle
roots and EN/CN translation checks pass. These counts cover different boundaries
and are not that many independent end-to-end journeys.

`actual-ui/report.json` records EN/light cancel and create, creation from a
locally published source, an injected private-reply loss after canonical commit,
normal restart and recovery of the same result while the synthetic provider is
signed out. CN/dark cancellation, explicit zero and cleared ceilings, and a
final normal restart also pass. Source rows, account namespaces,700-token shared
account declaration, capacity grants and engagements are compared directly.
Configuration creation/recovery produces no additional provider RPC. The
separate native tests cover previously offered sources, authority/namespace
fencing, qualified profile changes, rollback, source CAS and command collisions.

The actual window fixture uses a fresh private installation, an existing local
Matrix test account and an offline provider metadata fixture. It performs no
provider inference and does not verify real OAuth persistence. Original captures
are reviewed in `visual-review.json`; this is macOS hidden-native Metal evidence,
not GPU-free headless, mobile or whole-app UX acceptance. The owned fixture is
stopped after the journey. `.run/management45-promotion/manifest.json` and
`.run/management45-activate-{owner,manager,coordinator,admin}/report.json` are the
separate promotion/activation receipt locations when those steps occur.

Broader admitted-resource amendment, publication/withdrawal, deletion, daily cap,
account import and full JavaScript/all-platform parity remain unfinished.
