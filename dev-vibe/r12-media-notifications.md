# R12: explicit media playback and opt-in system notifications

Scope confirmed by the owner: media and notifications first; polls and calls remain unsupported and say so in the UI.

Audio/video messages expose **Save and play**. The existing R05 transport streams into its private, verified file and checks encrypted-media integrity before Save As. Only after a successful user-chosen save and a current-account fence does the system player receive a file URL. The player reads a user-owned file, so private-cache retirement cannot break playback; the saved copy is intentionally retained after logout. No whole-file Vec, private cache path, expiring share ticket, or Matrix media URL is passed to another process. Automatic opening accepts only listed audio/video extensions, excluding executable, shortcut, HTML and playlist types. Unsupported extensions/codecs or launcher errors leave the saved file available and explain the failure. This is external-player playback, not an embedded decoder or a claim that every codec is supported.

Notifications are opt-in and default off for old/new preferences. The explicit test button requests macOS permission; restoring settings never prompts. SDK push actions govern room messages, including encrypted events without exposing plaintext. Self messages, historical timestamps, foreground activity and muted/no-notify events are excluded. A session-fenced, 64-ID deduplication window, two-second rate limit and one actual OS worker bound work. Dropping an async waiter retains the permit until the original OS operation ends. Agent attention uses the same generic path. Notification text contains no sender, room, message body or URL. OS request acceptance is labelled separately from actual display, which Focus/policy can suppress.

macOS uses UserNotifications with an app-bundle preflight, authorization status and completion callbacks; an unbundled build reports that it cannot request permission. Linux uses the desktop notification portal with the existing async-std ashpd feature, avoiding a conflict with dark-light. Windows uses WinRT toast requests and requires a registered installed app identity; unpackaged identity failures are explicit. Windows packaging/identity and Linux portal delivery still need target-platform qualification. OS notification appearance and external-player decoding have not been certified by unit tests, and this PR remains draft pending that qualification. There is no activation/deep-link claim.

Local validation includes notification privacy/eligibility and old-preference tests, unbundled permission preflight, media-extension restrictions, actual audio/video rendering hints, the existing streaming/decryption/large-file gates, translation completeness, and the combined Desktop regression run. Exact final counts are attached on the PR after completion. New dependency versions are pinned; unrelated lockfile resolution changes are excluded. Matrix SDK and Makepad pins are unchanged.

Duplication reviewed against Desktop open/history through #72 (including unrelated #71 multi-invite) and Client #20/#21 attachment hardening. Existing transport and share work is reused; no matching media-launch/notification implementation PR was found. Stacked on R13 #72; R14 is already covered by R03 #57 and must not receive a duplicate PR.

The macOS test is scheduled five seconds ahead with guidance to switch apps, because foreground presentation normally requires a delegate. The code preserves an embedding host's delegate. Disabling notifications/logout removes this module's pending request. Normal background activity is immediate.

A full-suite failure exposed that Makepad can assign bundle metadata even to an unbundled test binary. The original identifier-only preflight was insufficient and an unsolicited cleanup call aborted at UserNotifications. The corrected preflight requires an actual .app/Contents/MacOS executable and Info.plist; cleanup never initializes a center unless this process submitted a request. A guarded Objective-C exception boundary reports an unavailable center and latches a failed initializer instead of retrying it. The aborted receipt is preserved; it is not counted as passing.

## Live macOS follow-up

A real two-account run reproduced a missed background-message notification: the session was current, notifications enabled, the event fresh and the SDK push action `notify`, but a stale window-focus hint remained true while Chrome was the actual active application. macOS now reads `NSRunningApplication.currentApplication.isActive`, an atomic/thread-safe application activity property, instead of trusting the window hint. A background-process regression sets a stale true hint and verifies it cannot suppress an eligible message. Preference changes also refresh their status label immediately.

Live evidence and final qualification are recorded separately under `.run/r12-native-20261112`; temporary diagnostics contain boolean gates only, never message text, user IDs or tokens. The original ordinary-launch dependency is the existing R01 #55 wrapper, not another R12 implementation change.
