# R08: recoverable permission-status failures

R08 covers the remaining SharedPermissionNotice failure flow. Desktop19/23 already address daemon custody/device setup and Client49 addresses an older hidden-notice lifecycle; those are related rather than complete fixes for error classification and the unconditional two-second retry. No matching open Desktop PR was found. This PR stacks on R07/60, preserving the prior official SDK/framework pins and fixes.

## Behavior

- Permission reads retain NativeError HTTP status at the central management boundary. Existing string-result APIs remain byte-compatible for mini-app callers. Matrix authorization and local daemon errors use stable codes; arbitrary server text, URLs and credentials are never displayed. Unrecognized errors stop automatic polling and expose a manual check.
- HTTP401/authentication errors offer Sign in again;403 explains resource-owner access and offers My Agents;404/405/501 unsupported operations and known daemon/setup failures stop polling and point to My Agents. An expired temporary management handle retries as transient rather than incorrectly logging the user out. No recovery button starts an Agent or changes a budget/permission.
- Network/authorization-read timeouts,408/429 and retryable5xx use nominal5/10/20/40/60-second exponential backoff, +/-20% jitter with an absolute60-second cap. A fresh successful read resets the failure counter and restores healthy two-second status polling. Manual Refresh status only reads current status. Rebinding/redraw/hide/reopen preserves an existing failed-read deadline or permanent pause. The one-hour simulated extreme/mid jitter fixtures stay below85 automatic reads versus the former roughly1800.
- Failures preserve last successful check time (UTC), explain the recovery route and next retry/pause, and disable decisions from stale rows. Malformed successful payloads cannot be treated as fresh empty permission lists. Recovery labels wrap and actions fill narrow panes; both catalogs include the new text.
- Requests have a30-second observer deadline and are scoped to account epoch, exact SDK revision, service identity, room, thread and nonce. Hiding/dropping/rebinding cancels the tracked observer and invalidates its result; reopening an interrupted check fetches fresh status. A request-owned management handle retires even on timeout/cancellation; borrowed mini-app managers retain their original ownership.
- Automatic retries always issue SharedApprovals reads. Approve/deny is only sent from an explicit valid current card action. Lost/failed/interrupted decisions are reported as unconfirmed; neither success nor execution is inferred and no decision is replayed automatically. A fresh authoritative status is needed before decision buttons become available again.

## Validation and limits

Tests cover status/code classification, dynamic English/Chinese catalog coverage, one-hour retry counts, jitter/cap/reset/permanent pauses, real widget actions for login/My Agents, stale decision disabling, malformed reads, actual observer cancellation, hidden/room/thread/account/SDK/nonce/identity fences, unknown decisions and real Makepad layout at280/360/560/900px. Existing activity-spinner/no-timeline-redraw tests remain intact. The complete library and required release runner counts are recorded in the PR description.

The bridge currently exposes status and stable code rather than Retry-After headers; backoff does not claim to implement an HTTP retry-header scheduler or detect OS offline state. Query timeout is not proof an in-flight mutation failed; underlying native ownership and journals remain authoritative. Local headless macOS fixtures do not certify actual Windows/Linux UI, production login, OS service setup or recipient/model execution. Existing unrelated warning-as-error debt remains unchanged. No SDK upgrade, service auto-start, permission grant or live business call is part of this change.
